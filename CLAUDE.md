# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

bazelex (binary `bazelex`) dumps the static target graph from `bazel query` into a SQLite database so it can be explored with SQL. `README.md` has usage, example queries and the schema rationale.

## Commands

Bazel is the build system (version in `.bazelversion`, use Bazelisk). The Go toolchain is managed by Bazel, so no local Go install is needed.

```sh
bazel test //...                                  # all tests
bazel test //internal/graphdb:graphdb_test --test_filter=TestLoad   # one test
bazel run //cmd/bazelex -- -db /tmp/g.sqlite      # run against this workspace
bazel run //:gazelle                              # after adding/removing Go files or imports
bazel run @io_bazel_rules_go//go -- mod tidy      # after changing Go dependencies
bazel run @io_bazel_rules_go//go -- fmt ./...     # gofmt
```

`BUILD.bazel` files are generated by gazelle. `go.mod` is the source of truth for Go dependencies: `MODULE.bazel` reads it through `go_deps.from_file`, and `mod tidy` also updates the `use_repo` list there.

Run the tool from inside a workspace. Under `bazel run`, `main` changes into `BUILD_WORKING_DIRECTORY` first, because Bazel refuses to be invoked from the runfiles tree. Keep that if you touch `run` in `cmd/bazelex/main.go`.

## Architecture

- `cmd/bazelex/`: flags, runs `bazel query --output=streamed_proto --keep_going` (default pattern `//...:all-targets`, because plain `//...` returns rules only) or reads that stream from stdin, then calls `graphdb.Load`.
- `internal/graphdb/`: `Schema` (the DDL, with column semantics documented inline) and `Load`, which reads length-delimited `Target` messages and writes `target`, `edge` and `attribute` rows in one transaction. After all inserts, one `UPDATE` resolves `edge.to_id`. It stays NULL for labels not in the loaded graph, such as external repos.
- `cmd/bazelex_ui/` and `internal/ui/`: a read-only web page that runs the README's example queries against a database written by `bazelex`. `main.go` only handles flags and opening the database. `internal/ui` has the canned queries (`queries.go`), the handler and pagination (`server.go`) and the page template (`index.html`). The template is generic: it loops over the queries, so adding an entry to `queries.go` is enough to show a new query, with no template change. `graph.go` and `graph.html` are a second page, `GET /graph`: it loads the package quotient graph from `rule_dep` on first use, takes the neighborhood of a package (or of its dependency cycle) out to a depth, and draws it with `go-graphviz` (Graphviz as WASM, no system `dot`). Keep the node cap and read `docs/graph-rendering.md` before changing the layout, because Graphviz layout time grows steeply with edges. A small script in the template refreshes one query in place by fetching `GET /q/{id}` (the `inner` template), and the page works without it. Like `bazelex`, `main` changes into `BUILD_WORKING_DIRECTORY` first.
- Bazel's query proto bindings come from the published `github.com/bazel-contrib/buildtools/v10` module (`build_proto`), not a local copy. `MODULE.bazel` has a `go_deps.gazelle_override` for that module (`build_file_generation = "clean"`, `gazelle:proto disable`) so it compiles its checked-in `build.gen.pb.go` as plain Go. Without the override, Bazel compiles protoc from source, which is very slow.

Edge extraction (`ruleEdges` and `labelsOf` in `load.go`) is the part that takes care:

- Edges come from every label-typed attribute kind, including each branch of `select()`. Select keys are recorded with `attr = '<select_condition>'`.
- `rule_input` entries that no attribute accounts for become `attr = '<implicit>'` edges.
- Generated files get a `<generating_rule>` edge to their rule.
- Duplicates within a rule are collapsed.
- Non-label attributes go to the `attribute` table via `ruleAttrs`: explicitly set ones only, plus `visibility`. `select()` values are skipped.
- Only `query` is supported, not `cquery`.
