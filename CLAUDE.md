# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

bazelex (binary `bazelex`) dumps the static target graph from `bazel query` into a SQLite database so it can be explored with SQL, a web UI (`bazelex_ui`) or the command-line interface (`bazelex_cli`). `README.md` has usage, example queries and the schema rationale.

## Commands

Bazel is the build system (version in `.bazelversion`, use Bazelisk). The Go toolchain is managed by Bazel, so no local Go install is needed.

```sh
bazel test //...                                  # all tests
bazel test //internal/graphdb:graphdb_test --test_filter=TestLoad   # one test
bazel run //cmd/bazelex -- -db /tmp/g.sqlite      # run against this workspace
bazel run //:gazelle                              # after adding/removing Go files or imports
bazel run @io_bazel_rules_go//go -- mod tidy      # after changing Go dependencies
bazel run @io_bazel_rules_go//go -- fmt ./...     # gofmt
```

`BUILD.bazel` files are generated by gazelle. `go.mod` is the source of truth for Go dependencies: `MODULE.bazel` reads it through `go_deps.from_file`, and `mod tidy` also updates the `use_repo` list there.

Run the tool from inside a workspace. Under `bazel run`, `main` changes into `BUILD_WORKING_DIRECTORY` first, because Bazel refuses to be invoked from the runfiles tree. Keep that if you touch `run` in `cmd/bazelex/main.go`.

## Architecture

- `cmd/bazelex/`: flags, runs `bazel query --output=streamed_proto --keep_going` (default pattern `//...:all-targets`, because plain `//...` returns rules only) or reads that stream from stdin, then calls `graphdb.Load`.
- `internal/graphdb/`: `Schema` (the DDL, with column semantics documented inline) and `Load`, which reads length-delimited `Target` messages and writes `target`, `edge` and `attribute` rows in one transaction. After all inserts, one `UPDATE` resolves `edge.to_id`. It stays NULL for labels not in the loaded graph, such as external repos.
- `internal/engine/`: the exploration engine shared by both front-ends. It runs a SQL query (`Query`, `QueryPage`), loads the graph as Mangle facts and evaluates a program (`Datalog`), and builds the build graph's quotient graphs (`PackageGraph`, `CondensedGraph`). It returns neutral tables of values and has no presentation concerns, so it depends on `database/sql` and Mangle but not on `html/template` or Graphviz.
- `internal/quotient/`: quotient graphs of the build graph. `Graph` is a weighted digraph, `Partition` collapses its nodes into groups, and `ComponentIndex`/`Components`/`Condense` are Tarjan's strongly connected components, which turn a cyclic graph (the package graph) into a DAG. The engine loads the package quotient and condenses it with `Condense`.
- `cmd/bazelex_cli/` and `internal/cli/`: the command-line front-end. `main.go` has the flags and the `sql` and `datalog` subcommands (the subcommand comes first, then its flags; the input is the last argument, or stdin, or `@file`). `internal/cli` renders the engine's results as Markdown, JSON or CSV.
- `cmd/bazelex_ui/` and `internal/ui/`: the web front-end. It is a read-only web page that runs the README's example queries against a database written by `bazelex`. `main.go` only handles flags and opening the database. `internal/ui` has the canned queries (`queries.go`), the handler and pagination (`server.go`, which runs a page's cheap queries in a bounded pool, sized by `--parallel`) and the page template (`index.html`). The template is generic: it loops over the queries, so adding an entry to `queries.go` is enough to show a new query, with no template change. `graph.go` and `graph.html` are a second page, `GET /graph`: it loads the package quotient graph from `rule_dep` on first use, takes the neighborhood of a package (or of its dependency cycle) out to a depth, and draws it with `go-graphviz` (Graphviz as WASM, no system `dot`). Keep the node cap and read `docs/graph-rendering.md` before changing the layout, because Graphviz layout time grows steeply with edges. Drawings are cached in memory by (package, depth, cycle), which is safe because the database is read-only, and `GET /graph.dot` and `GET /graph.svg` serve the cached DOT and SVG as downloads. A small script in the template refreshes one query in place by fetching `GET /q/{id}` (the `inner` template), and the page works without it. A third page, `GET /datalog` (`datalog.go`, `datalog.html`), asks the engine to evaluate a [Mangle](https://github.com/google/mangle) program over facts it translates from the database on first use: `target/3`, `dep/2`, `edge/3` and the quotient facts `qnode/2`, `qedge/4` and `qmember/3`, with labels as string constants because a Bazel label is not a valid Mangle name constant. The quotient facts describe the package graph and its SCC condensation (`CondensedGraph`), so a program can reason at package or dependency-cycle granularity. The example programs are in `datalogPrograms`, and the page shows at most `maxDatalogRows` rows of each relation; a program that derives more than the engine's `MaxFacts` facts is stopped with an error. Mangle is pinned at v0.4.0, the last version published under the `github.com/google/mangle` path (see TODO.md). Like `bazelex`, `main` changes into `BUILD_WORKING_DIRECTORY` first.
- Bazel's query proto bindings come from the published `github.com/bazel-contrib/buildtools/v10` module (`build_proto`), not a local copy. `MODULE.bazel` has a `go_deps.gazelle_override` for that module (`build_file_generation = "clean"`, `gazelle:proto disable`) so it compiles its checked-in `build.gen.pb.go` as plain Go. Without the override, Bazel compiles protoc from source, which is very slow.

Edge extraction (`ruleEdges` and `labelsOf` in `load.go`) is the part that takes care:

- Edges come from every label-typed attribute kind, including each branch of `select()`. Select keys are recorded with `attr = '<select_condition>'`.
- `rule_input` entries that no attribute accounts for become `attr = '<implicit>'` edges.
- Generated files get a `<generating_rule>` edge to their rule.
- Duplicates within a rule are collapsed.
- Non-label attributes go to the `attribute` table via `ruleAttrs`: explicitly set ones only, plus `visibility`. `select()` values are skipped.
- Only `query` is supported, not `cquery`.
